Repository truth that must shape implementationA live audit of the repository reveals several important facts that should override stale descriptions in older plans.## 2.1 Current architecture strengthsJoBot already contains substantial production-oriented building blocks:* Python 3.11+ core.* SQLite WAL persistence and encrypted local secrets.* Provider-neutral model routing and cost awareness.* A 12-phase application submission pipeline with DoD gates.* Site adapter abstractions for multiple ATS/job sources.* Circuit breakers and verification hooks.* Tauri 2 + React GUI shell and a JSON-RPC sidecar.* Resume tailoring, cover letters, ATS checking and PDF generation.* Job discovery, deduplication and JobSpy integration.* PII masking, vault/keyring integration, policy controls, scheduling, notifications, tracker/analytics, mock ATS fixtures and a broad automated test suite.* GitHub Actions, CodeQL, Dependabot, SBOM/provenance, Docker packaging and PyPI publishing infrastructure.* Project state/queue files that already align with the `AGENTS.md` filesystem-first model.## 2.2 Current correctness gaps found directly in code### Durable task graph is currently not durable`src/jobot/task\\\\\\\_graph.py` stores tasks in an in-memory dictionary. Task claiming mutates in-memory objects and therefore is not an atomic database-backed lease protocol. The implementation contract must move task ownership, attempts, leases, heartbeats, recovery and task events into durable storage.### Application pipeline has an architectural split between declared and enforced policy`ApplicationSubmissionPipeline` has a `PolicyEngine`, but the current phase execution path does not make policy evaluation the universal pre-side-effect gate. Phase 10 can pause on trust level, while phase 11 performs the external submit operation. The refactor must make policy/risk evaluation mandatory immediately before every consequential side effect, not merely an injected dependency.### Current pipeline-level idempotency is necessary but insufficientThe pipeline derives an idempotency key from `job\\\\\\\_url` and `profile\\\\\\\_id`, detects an existing application, and avoids some duplicate behavior. This must be extended to an external-effect ledger so ambiguous local state can never trigger a duplicate remote submission.### Verification needs to become a real reconciliation protocolThe current phase 12 verification marks an application `VERIFIED` when adapter verification succeeds, but the master runtime needs a first-class `UNKNOWN` state, evidence correlation, confirmation identifiers, replay protection, and recovery behavior for uncertain outcomes.### Database migrations are currently additive and implicit`DatabaseManager.migrate()` uses ad-hoc `\\\\\\\_ensure\\\\\\\_column()` logic. That is adequate for early development but not for a long-lived product with upgrade, rollback and recovery guarantees. Introduce checksummed, versioned migrations.### LLM streaming is still stubbedAt least several provider classes still raise `NotImplementedError` for streaming. This directly blocks real-time UX and efficient long-form workflows. Streaming must be implemented behind one provider-independent interface, with tests for all provider families and a graceful fallback to non-streaming.### Tauri shell permissions are broader than necessaryThe current capability configuration gives the sidecar spawn/execute permissions with unrestricted argument matching (`args: true`). This must be replaced with least-privilege command/argument allowlists.### Version and packaging metadata drift existsThe current `pyproject.toml` declares version `0.1.0`, supports Python `>=3.11`, and still uses the deprecated table-form license declaration while the GUI/release plans target a different release version. Establish one authoritative version source and make all packaging metadata derive from it.### Documentation is stale relative to the actual project stateThe current README says the authoritative specification is an older merge plan and still describes Patchright integration as being in progress. This is now incompatible with a release-ready product narrative and must be replaced by generated, tested documentation that reflects reality.### Policy defaults need redesign, not just more codeThe current `PolicyEngine` includes large site-specific daily application limits. The future risk model must separate recommendation limits, preparation limits, submission limits, per-site trust, per-action risk, and user-defined caps. High numerical caps must not be mistaken for production-safe autonomy.## 2.3 Repository hygiene findingsThe repository currently contains multiple planning generations and very large historical documents alongside the active product. Examples visible in the tree include large historical planning files, root plan files, `repo\\\\\\\_research.md`, `worklog.md`, multiple implementation contracts, and old merged plans. The cleanup phase must establish one canonical documentation hierarchy, archive historical material, and delete only files proven redundant.The cleanup must be evidence-driven: classify every tracked file as active runtime, active test, active documentation, generated artifact, historical record, duplicate, obsolete, secret-like, or unknown. Unknown files are investigated before deletion.\---# 3\. Final product definition## 3.1 Product promiseFor `v1.0`, JoBot should truthfully promise:> JoBot discovers, evaluates, prepares, verifies, submits where technically and policy-authorized, and tracks job applications across a defined set of supported sources and workflows. It provides durable state, human-governed automation, crash recovery, evidence, auditable execution, privacy-preserving local operation, and release-gated evaluation.Do not promise universal job-board support, unrestricted autonomy, guaranteed interview outcomes, or platform-safe automation where the underlying platform does not authorize it.## 3.2 User-visible capabilitiesAt release, an average user should be able to:1. Install JoBot from a documented distribution channel.2. Run `jobot doctor` and receive actionable environment status.3. Import an existing resume and create a secure candidate profile.4. Configure LLM providers and privacy settings without editing source code.5. Discover jobs across supported sources.6. See normalized jobs and match explanations.7. Tailor a resume and cover letter using grounded candidate facts.8. Review form questions and receive profile-grounded answers.9. Prepare an application without committing an external side effect.10. Approve, edit, reject or defer consequential steps.11. Submit through supported and authorized mechanisms.12. Verify submission using independent evidence.13. Recover after process, browser, network or provider failures.14. Track applications, interviews, follow-ups, contacts and outcomes.15. Inspect cost, evidence, logs, incidents and decisions.16. Export their data and purge it locally.17. Upgrade from one release to the next without losing state.## 3.3 Autonomy modelAutonomy must be scoped, explicit and measurable.|Risk|Example|Default behavior||-|-|-||R0|Local read/inspect|Automatic||R1|Public job discovery|Automatic||R2|Resume/cover generation|Automatic, with verification||R3|Application preparation|Automatic, approval before external side effect||R4|Save/submit action on a trusted authorized integration|Policy-controlled||R5|Final job submission on a browser site|Human approval by default||R6|Recruiter outreach / external messaging|Human approval||R7|Credential/secret modification|Human approval||R8|Irreversible/high-impact action|Human only|Trust must be scoped to the target, action type, integration, skill or adapter. There is no single global `autonomous=true` switch.\---# 4\. Phase 2 - Durable execution coreThis phase implements the central architectural recommendation from Plan 1 and aligns the repository with `AGENTS.md`.## 7.1 Persistent task entitiesIntroduce durable entities:```textGoalTaskTaskDependencyTaskAttemptTaskLeaseTaskEventTaskArtifact```Task states:```textPENDINGREADYCLAIMEDRUNNINGWAITINGRETRYINGVERIFYINGCOMPLETEDFAILEDQUARANTINEDCANCELLEDUNKNOWN```## 7.2 Atomic task claimingClaiming MUST be a database transaction, not an in-memory mutation.Required semantics:* worker identifier.* lease acquisition time.* lease expiry.* heartbeat.* attempt number.* strategy used.* last checkpoint.* failure reason.* recovery eligibility.* cancellation token.Two workers must never hold the same active lease.## 7.3 Event ledgerCreate a durable append-only event table:```textevent\\\\\\\_idaggregate\\\\\\\_typeaggregate\\\\\\\_idevent\\\\\\\_typeevent\\\\\\\_versionpayloadactorcorrelation\\\\\\\_idcausation\\\\\\\_idcreated\\\\\\\_at```Event examples:```textGoalCreatedTaskCreatedTaskClaimedTaskStartedToolInvokedToolCompletedToolFailedApprovalRequestedApprovalGrantedApprovalRejectedBrowserSessionStartedBrowserSessionLostApplicationPreparedApplicationSubmittedApplicationVerifiedApplicationUnknownBudgetExceededWorkerDisconnectedRunResumedRunQuarantinedMemoryUpdatedEvalCompleted```## 7.4 Event busAfter the event ledger is stable, add a typed in-process event bus with subscribers for:* alerts.* telemetry.* GUI push updates.* analytics.* persistence projections.* incident handling.Keep the event ledger as the source of truth; the event bus is a delivery mechanism, not the canonical state store.## 7.5 CheckpointingEvery long-running harness must support:* start checkpoint.* intermediate checkpoint.* approval waitpoint.* tool result checkpoint.* verification checkpoint.* resume after process death.* retry after recoverable failure.* quarantine after unsafe ambiguity.## 7.6 Retry policyDefault:* retry once with the same strategy for transient failures.* if it fails again, change strategy or escalate.* never retry irreversible effects without reconciliation.* never retry on hard policy denials.* backoff must be explicit and bounded.## Exit criteriaKill a worker at every major phase and demonstrate correct recovery without task duplication or lost durable state.\---# 8\. Phase 3 - Application state machine, effects, approval and reconciliation## 8.1 Application state machineDefine explicit transitions for:```textDISCOVEREDNORMALIZEDMATCHEDSHORTLISTEDPREPARINGREADY\\\\\\\_FOR\\\\\\\_REVIEWPENDING\\\\\\\_APPROVALSUBMITTINGSUBMITTEDVERIFYINGVERIFIEDUNKNOWNFAILEDQUARANTINEDCANCELLEDREJECTEDEXPIRED```Transitions must be validated against an explicit table. Do not allow arbitrary enum mutation.## 8.2 External-effect ledgerIntroduce:```textExternalEffect  effect\\\\\\\_idtask\\\\\\\_idapplication\\\\\\\_ideffect\\\\\\\_typeidempotency\\\\\\\_keyrequest\\\\\\\_hashstarted\\\\\\\_atcompleted\\\\\\\_atstatusexternal\\\\\\\_referenceverification\\\\\\\_statecompensation\\\\\\\_state```Before an external side effect:1. compute deterministic effect identity.2. reserve the effect.3. evaluate policy.4. obtain approval where required.5. execute once.6. capture evidence.7. reconcile remote state.8. finalize ledger record.If local state is ambiguous after a crash, reconcile instead of replaying the effect.## 8.3 Durable approvalsCreate persistent `ApprovalRequest` entities containing:* proposed action.* arguments.* risk level.* evidence.* policy rationale.* expiry.* requester/actor.* decision timestamp.* edited arguments.* resulting effect id.Supported decisions:```textAPPROVEEDITREJECTDEFERCANCEL```CLI, GUI and MCP must all use the same approval entity and lifecycle.## 8.4 Policy as an execution boundaryEvery consequential action must pass:```textaction proposal  -> policy  -> risk score  -> trust check  -> budget check  -> approval check  -> idempotency/effect reservation  -> execute  -> verify```The policy engine should return typed reasons and machine-readable decisions.## 8.5 Risk modelCompute risk from:```textaction target reversibility credential access external side effect personal data financial cost volume confidence integration trust skill trust```Use policy rules for hard blocks and a risk score for escalation/approval routing.## 8.6 Correct the response timestamp semanticsThe current database code treats statuses such as `SUBMITTED` and `VERIFIED` as response statuses for `responded\\\\\\\_at`. That conflates application submission with employer response. Split these concepts into:* `submitted\\\\\\\_at`.* `submission\\\\\\\_verified\\\\\\\_at`.* `first\\\\\\\_employer\\\\\\\_response\\\\\\\_at`.* `current\\\\\\\_outcome`.Add migration and backfill logic.## 8.7 Reconciliation serviceImplement reconciliation routines for:* application submission.* job expiry.* provider status.* email/application status signals.* browser session ambiguity.* remote job identity changes.Unknown is not failure and not success. Unknown is a durable state requiring a next action.## Exit criteria* Duplicate external submissions are provably prevented under crash/restart tests.* Approval survives restart.* A synthetic crash after submit but before local persistence is recoverable through reconciliation.\---# 9\. Phase 4 - Browser reliability and adapter platform## 9.1 Browser subsystemCreate explicit services for:```textBrowserSessionManagerBrowserPoolProfileStoreSessionPersistenceNavigationNamedActionsSelectorRegistrySelectorHealingEvidenceCaptureRateLimitDetectorSiteHealthRecoveryCAPTCHA Boundary```## 9.2 Deterministic browser actionsPrefer semantic, stable locators and named actions. Playwright documents locators as the primary mechanism with built-in auto-waiting/retry behavior and actionability checks. JoBot should build its reliability layer on top of those deterministic primitives instead of encoding entire workflows as free-form model output.## 9.3 Selector registryCreate a central registry:```textsite -> workflow -> step -> candidate locators```Support:* multiple candidate selectors.* confidence scoring.* fallback order.* healing records.* DOM drift test fixtures.* selector health metrics.Do not allow silent AI rewriting of selectors in production. Proposed healing must pass bounded validation.## 9.4 Browser evidenceFor consequential actions capture:* pre-action screenshot when useful.* relevant DOM/form snapshot.* named action and arguments.* post-action screenshot.* result.* verification signal.* trace/application ids.Avoid storing massive raw browser state indefinitely. Apply retention and deduplication.## 9.5 Site healthTrack per integration:* success rate.* median latency.* timeout rate.* verification failures.* selector drift.* circuit breaker state.* rate limit signals.* recent user overrides.Auto-demote unreliable integrations to supervised/manual mode.## 9.6 Platform terms and safety boundaryLinkedIn currently prohibits unauthorized automated access and scraping in its User Agreement. Therefore, LinkedIn automation must never be implemented as a promise to bypass controls. Any browser automation work must include an explicit ToS/authorization review, user warning, rate controls, and a manual-assist fallback.The same principle applies to every platform: do not defeat CAPTCHAs, security boundaries, anti-bot controls, access controls or usage limits. A CAPTCHA subsystem, if retained, should be a detection/escalation boundary rather than an unconditional bypass mechanism.## 9.7 Adapter family generalizationGeneralize common ATS patterns:* Workday/CXS style APIs.* Workable.* Recruitee.* Teamtailor.* BambooHR.* other compatible JSON feeds.Use a shared transport/parser abstraction with per-site configuration and small site-specific modules.## 9.8 Adapter boundary schemasDefine strict Pydantic contracts for:* `JobPosting`.* `ApplicationForm`.* `ApplicationResult`.* `SubmitOutcome`.* `VerificationResult`.* `SiteHealth`.Invalid adapter output should fail safely and be quarantined.## 9.9 Direct ATS API integration - corrected policyKeep the idea of direct API submission, but implement it only where the necessary authorization is legitimately available.For example, Greenhouse exposes public job-board reads but its application submission endpoint requires Basic Auth with an API key; Ashby's application form endpoint also requires authorization. These are not equivalent to unrestricted public applicant APIs.Therefore, create three explicit adapter modes:1. `PUBLIC\\\\\\\_READ`: public discovery/normalization.2. `USER\\\\\\\_AUTHORIZED\\\\\\\_API`: direct submission with valid user/employer-authorized credentials.3. `BROWSER\\\\\\\_ASSISTED`: hosted form/browser flow where direct API submission is not legitimately available.Never fake an API flow merely because an endpoint exists.## Exit criteriaMock ATS workflows survive injected browser, selector, timeout and network failures. Every supported production adapter documents its authorization mode and verification behavior.\---# 10\. Competitive feature synthesisThe product should absorb underlying capabilities from competing systems, not copy proprietary implementations.Current commercial products emphasize centralized tracking, job bookmarking, personalized matching, tailored resumes, ATS optimization, autofill, contacts, metrics and career insights. Jobright currently markets job matching, autofill, tailored resumes and insider connections, while Teal emphasizes tailored resumes, job tracking, ATS checks, profile import and job matching. Simplify emphasizes a job tracker integrated with applications and an extension-driven autofill experience. These confirm that workflow continuity is table stakes for a serious job-search product.JoBot's differentiation should remain:1. durable verified execution rather than fragile macros.2. local-first privacy rather than mandatory hosted processing.3. candidate-truth grounding rather than generic generation.4. evidence-backed submission verification.5. human-governed autonomy rather than opaque "set and forget" execution.6. cost-aware multi-model routing.7. auditable trajectories and release-gated evaluations.8. extensible career-OS architecture rather than a single board integration.\---# 26\.
